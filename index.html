STE → skill mapping

Section 1 — ~2 min. You’ve said why you care. Now why skills care — no bio callback longer than one sentence.

Four conventions

  • Skill-local terms — small glossary; no synonym drift
  • One meaning per word — if run means execute, don’t also mean chat turn
  • Short imperative steps — one action per sentence; numbered order
  • Hard vs soft isolated — must / do not mean it; park prefer separately
Controlled language in one breath: limited vocabulary, one word / one meaning, short sentences, imperative steps. Not certification; not memorizing the dictionary. Skills are operational — when to load, what to do, what not to do, in order. Ambiguity → variance; STE-shaped writing buys consistency, not “smarter models.” Unsure of an STE clause number → say “STE spirit / approximate.” Never invent dictionary entries.

Anti-patterns (one breath)

  • Vague verbs: ensure / handle / consider
  • Nested if / unless / except
  • Soft rules mixed into hard steps
One breath only. If §0 ran long, cut this slide and go straight to before/after — never cut Example C or CTA.

Synthetic · Example A

Setup steps

Before

Before you change anything, ensure the environment is set up correctly and be mindful of missing dependencies. Handle install problems appropriately so the rest of the skill can proceed smoothly.

After
  1. From the repository root, run the project install command.
  2. Run the project typecheck (or tests if there is no typecheck).
  3. If install or typecheck fails, stop. Report the failing command and the error.
  4. Do not edit feature files until install and typecheck succeed.
Read Before aloud. Name the failure mode next. Reveal After (or already visible — pause for reading). After can be longer — unambiguous action beats brevity.

Synthetic · Example C

Deploy steps

Before

If the user asks for a deploy, unless they only wanted a dry run (except in production where you should always confirm), try to deploy and handle issues. Prefer not to bother them unless necessary.

After
  1. If the user asked for a dry run only: run the dry-run command. Report the result. Stop.
  2. If the deploy target is production: ask for explicit confirmation. Do not deploy before the user confirms.
  3. Run the deploy command for the named target.
  4. If deploy fails: report the failing command and the error. Do not claim success.
  5. Do not retry a failed production deploy with different flags unless the user asks.
Pause 2 seconds after revealing After. Bandwidth fallback: if screenshare lags, paste this After into chat and narrate. Exact tokens stay — dry-run, production, deploy command.

Synthetic · Example C

What the agent can misread

  • Nested unless / except — which branch wins?
  • “Try” / “prefer” / “handle” — optional tone
  • No early stop; no hard do not
Nested conditionals are where humans and agents both lose the thread. Soft verbs erase the stop points.

Nested unless/except and soft try/prefer/handle → ordered early exits and hard do nots.

Stretch · Synthetic · Example B

Edit steps

Before

Open the repo, inspect the codebase, and update the project tree so the application reflects the change. Keep the workspace consistent.

After
  1. Open the repository root.
  2. Find the files for this change.
  3. Edit only those files.
  4. Verify the app shows the change.
  5. Do not rename “repository” to “codebase,” “project,” or “tree” in this skill — use repository only.
Ambiguity that dies: repo / codebase / project / tree / workspace → one house term.

Stretch · Synthetic · Example D

Edit this skill

Before

You should generally prefer editing the skill, and make sure not to break things. Feel free to tidy other files if it seems helpful.

After
  1. Edit only the skill file the user named.
  2. Keep unrelated skills and config unchanged.
  3. After the edit, run the skill’s smoke check if one exists.
  4. Do not “tidy” other files unless the user asks.
Soft “should generally prefer / feel free” vs hard edit boundary and do not tidy.
